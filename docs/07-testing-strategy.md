# راهبرد آزمون فنی

آزمون‌پذیری بخشی از تعریف تکمیل محصول است، نه فعالیتی پس از پیاده‌سازی. هر تغییر در رتبه‌بندی، داده، رابط یا جریان مقایسه باید همراه با آزمون متناسب وارد مخزن شود.

## لایه‌های آزمون

### ۱. منطق و داده

- آزمون واحد رتبه‌بندی، گروه‌بندی و تولید توضیح؛
- اعتبارسنجی قراردادهای `course` و `search-query`؛
- تضمین باقی‌ماندن همهٔ دوره‌های معتبر در خروجی؛
- آزمون مرز بودجهٔ صفر تا ۳۰ میلیون تومان؛
- آزمون تغییر مهلت، ساعت هفتگی و سطح مهارت؛
- آزمون خروجی پایدار برای داده و query یکسان.

این لایه در حال حاضر با ۱۳ آزمون Python پوشش داده شده است.

### ۲. کامپوننت‌های React

- نمایش صحیح کارت دوره در حالت‌های مطلوب، منعطف، کششی و دادهٔ نامشخص؛
- رفتار ورودی جست‌وجو، slider بودجه، کنترل زمان، انتخاب سطح مهارت و checkbox اولویت‌ها؛
- نمایش دلیل رتبه، هشدار و تغییر لازم؛
- انتخاب و حذف دوره از نوار مقایسه؛
- حالت‌های خالی، خطا و شکست استخراج AI.

### ۳. یکپارچگی رابط و رتبه‌بندی

- تبدیل ورودی قابل‌ویرایش کاربر به query استاندارد؛
- بازرتبه‌بندی پس از تغییر هر محدودیت؛
- هماهنگی تعداد تب‌ها با گروه‌های واقعی خروجی؛
- حفظ گزینه‌ها هنگام عبور از مطلوب به منعطف یا کششی؛
- مقایسهٔ کنارهمی بر پایهٔ دادهٔ همان نتایج.

### ۴. مسیرهای انتها‌به‌انتها

- جست‌وجوی «ساخت RAG با Python» تا مشاهدهٔ سه پیشنهاد اصلی؛
- افزایش بودجه و تغییر گروه مجتمع فنی تهران؛
- افزایش زمان و تغییر گروه Bardia.ai؛
- تغییر سطح RAG یا LangChain و بازشدن دوره‌های دارای پیش‌نیاز؛
- انتخاب دو دوره و ورود به مقایسه در دسکتاپ و موبایل.

### ۵. کیفیت تجربه

- بررسی دسترس‌پذیری خودکار و دستی: کنتراست، ترتیب فوکوس، برچسب کنترل‌ها و استفاده با صفحه‌کلید؛
- آزمون responsive در عرض‌های ۳۹۰ و ۱۴۴۰ پیکسل؛
- کنترل خطای کنسول، درخواست‌های شکست‌خورده و layout shift؛
- آزمون بصری برای اجزای پایدار پس از تثبیت High-fidelity.

## ابزار پیشنهادی برای Frontend

- Vitest برای توابع و منطق Frontend؛
- React Testing Library برای رفتار کامپوننت‌ها؛
- Playwright برای مسیرهای انتها‌به‌انتها و responsive؛
- axe-core برای کنترل خودکار دسترس‌پذیری.

## معیار پذیرش

1. اجرای یک فرمان، تمام آزمون‌های Python و Frontend را اجرا کند.
2. هیچ تغییر در منطق رتبه‌بندی بدون آزمون شکست‌خورندهٔ قبلی پذیرفته نشود.
3. جریان جست‌وجو، تغییر محدودیت و مقایسه در دسکتاپ و موبایل آزمون انتها‌به‌انتها داشته باشد.
4. حالت‌های `unknown` و نبود تطابق کامل در تست‌ها پوشش داده شوند.
5. شکست آزمون یا دسترس‌پذیری، build تحویلی را ناموفق کند.
